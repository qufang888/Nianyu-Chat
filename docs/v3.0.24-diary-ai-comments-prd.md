# v3.0.24 日记 AI 留言增量 PRD

## 0. 项目信息

- **Language**: 中文（与用户需求一致）
- **Programming Language**: 沿用现有 Electron + Vite + React + TypeScript + CSS（**不引入新技术栈**）
- **Project Name**: `v3_0_24_diary_ai_comments`
- **基线**: HEAD `52e934e`（已发布 v3.0.23）→ 目标 **v3.0.24**
- **原始需求复述**（逐字保留语义）:
  - 修复日记编辑器「可见人物」界面显示错乱；人物很多时会超出外框，需修复为正常样式。
  - AI 自动留言分**普通模式 + NHPP 模式**两种。普通模式内含三种触发：①时段留言（用户设置起止时段，时段内某一刻留言）；②几分钟后留言（相对触发时刻延迟）；③固定时间留言。均可在设置里设置。可让每个 AI 人物在不同时间段/不同固定时间留言。
  - 留言可用 NHPP 机制，参考现有 nhpp 主动消息。
  - 每个日记每个 AI 人物默认只能有一条留言；除非用户回复了该留言。回复后 AI 立即查看用户回复内容并再回复一次，聊天中提到也会生效、不会忘记这件事（需做好留言回复功能）。
  - 打开免打扰后 AI 留言仍生效，但无任何提示；未打开时有提示（显示日记标题 + 谁留言了）；AI 留言的回复也要提醒，与新消息提醒相同。
  - 修复完检查无误后上传 GitHub。

## 4. 留言调度状态机（P0-3 / P0-4）

### 4.1 「一人物一留言」锁状态机（核心约束）

```
NO_COMMENT ──(调度触发/手动生成)──> COMMENTED(锁)
    ^                                    │
    │                              (用户回复该留言)
    │                                    ▼
    └──(AI 回复完成, 重新上锁)──── AI_REPLIED(锁)  [可再进入下一轮, 见 §10-Q1]
```

- **must**：每篇日记 × 每个角色，未回复状态下**最多 1 条**有效（未 `revoked`）AI 留言；已存在则调度器**跳过**，不重复生成。
- **must**：仅当用户对该留言**追加了回复**后，该角色才解锁"再回复一次"；AI 回复完成后重新上锁。
- **已定（Q1）**：**允许多轮回复**，但**每一轮 AI 回复都必须由用户的新回复触发，绝不自动连发**；每轮由 `awaitingUserReply` 控制状态（详见 §10-Q1）。状态机中 `AI_REPLIED(锁)` 后须等待用户**新的**回复才再次解锁，不得由定时器/心跳自行触发下一轮。

### 4.2 普通模式三子模式

| 子模式 | 排程规则（must） | 状态流转 |
|---|---|---|
| ①时段留言 `window` | 用户设 `start`/`end`（'HH:mm'，可跨午夜）。日记保存后，在 [start,end] 内**均匀随机取一时刻**（已定 Q3）触发一次；**每篇每角色每日最多 1 次**（已定 Q3，与一人物一留言锁一致）；若保存时已过当日窗口则顺延次日窗口。 | `pending → due(窗口内均匀随机点) → sent(锁)` |
| ②几分钟后 `delay` | 以**日记保存时刻**为起点，`T + delayMinutes` 触发一次。 | `pending → due(T+N min) → sent(锁)` |
| ③固定时间 `fixed` | 每天 `fixedTime`（'HH:mm'）触发；若日记创建晚于当日固定点则顺延次日。 | `pending → due(每日 fixedTime) → sent(锁)` |

- 三类均受「一人物一留言」锁约束：发送后即 `COMMENTED`，不再重复，除非进入 §4.1 的回复分支。
- 调度状态建议统一枚举：`pending | due | sent | skipped | superseded`；配置变更时对 `pending` 任务按 §10-Q4 已定口径处理（作废旧 `pending` 并按新配置重排；关闭 `enabled` 直接作废）。

### 4.3 NHPP 模式

- **must**：复用 `electron/proactive.ts` 的强度函数 / thinning 采样 / 反馈 / `dailyLimit` / `rescheduleProactive` / `heartbeatProactive`，**以依赖注入方式扩展**，不改动原主动消息（聊天）行为；原 `proactiveEngine==='nhpp'` 门禁继续生效。
- **作用域**：候选 key 从 `chatKey` 扩展为 `diary:{diaryId}:{roleId}`，每日上限、疲劳、反馈均按此 key 计。
- **生成门禁**：沿用 NHPP 原有"等回复 / 新鲜度 / 每日上限"判断层；「一人物一留言」锁作为**额外硬门禁**叠加（锁定即跳过，不采样不发送）。
- **勿扰区分（已定 Q2）**：NHPP 日记留言**沿用 `proactiveDnd` 窗口顺延**（原 NHPP 行为不回退，命中 DND 窗口就顺延生成）；它与托盘静默 `settings.silent` **语义分离**——`settings.silent`（§7）**只静音不停生成**。两者语义需在 UI 文案上区分清楚。

### 4.4 触发入口（不回退既有）

- 保留现有 `scheduleDiaryAi`（`electron/main.ts:5834`）在日记保存后的自动留言/自动总结链路；新增调度器**接管留言排程**，但"自动总结"行为不变。
- 保留 tone='skip'（低好感/坏心情不留言）判定（`planDiaryAiWork`），三类普通模式与 NHPP 均需经过该判定。
- 保留"手动重新留言/总结"按钮（`:454-455`）；手动重新留言属用户显式意图，**允许强制重生成**（旧留言软撤 `revoked`，见 §10-Q5 已定），但 **UI 必须二次确认**后方可执行。

### 5.1 设置项（落 `AppSettings`，`src/types.ts`）

```ts
type DiaryCommentMode = 'normal' | 'nhpp';
type NormalTrigger = 'window' | 'delay' | 'fixed';

interface DiaryCommentConfig {

    trigger: NormalTrigger;         // 'window' | 'delay' | 'fixed'

    dailyLimit?: number;
    freshnessMin?: number;
  };
}

// AppSettings 新增字段（可选，向后兼容；老用户无该字段 = 全部人物未启用自动留言）
diaryCommentSchedules?: Record<string, DiaryCommentConfig>; // key = roleId（全局，不按身份分，已定 Q6）
```

## 6. 留言 / 回复交互与约束（P0-5 / P0-6）

1. **展示**：日记卡片的 AI 留言区（`DiaryView.tsx:457-471`）在每条留言下渲染 `replies` 对话串，标注"我 / 角色名"与时间；未撤销才显示。
2. **用户回复**：每条留言/对话串底部提供「回复」输入框（P1 可折叠）。用户提交后：`replies.push({author:'user', ...})` → 立即落盘 → 触发 AI 回复生成。
3. **AI 回复生成（must）**：
   - system prompt 用 `buildSystemPrompt(role)`（人设 + 语气），并**显式注入该角色与用户的聊天上下文**（"聊天里提到也会生效、不会忘记"）——复用现有 `queryAI` 上下文组装 / `buildDiaryContextBlock` 门控。
   - **上下文注入（已定 Q7）**：**硬要求**包含「**用户本次回复原文 + 该留言串全部历史**」；其余按最近 N 条该角色聊天与既有 token 预算裁剪，**上限由架构师定**；须遵守 `collectArtifactsForRole` 门控，**不注入未授权产物**（未 `revoked`、身份册 + 可见名单双门控）。
   - prompt 要求 AI 针对用户所回复的内容作答。
   - 生成结果以 `{author:'ai'}` 追加到同一 `replies`，完成后重新上锁。
4. **约束**：
   - 无用户回复 → AI **绝不**自动追加第二条留言/回复（§4.1）。
   - **允许多轮（已定 Q1）**：AI 回复后须等待**用户新的回复**才解锁下一轮，**绝不自动连发**；每轮由 `awaitingUserReply` 控制。
   - 用户回复后 AI 回复**立即**生成（不进普通/NHPP 排程队列，属事件驱动）。
   - 回复也遵守禁用总开关 / 可见名单门控（`canRoleAccessDiary`）：角色被移出可见名单后不再为其生成回复。
   - 身份门控：回复沿用 `selfRoleId` 约束，不跨身份串台。
   - **手动强制重生成（已定 Q5）**：手动重新留言允许强制重生成、旧留言软撤 `revoked`，但 **UI 必须二次确认**后执行。

## 7. 通知 / 静默矩阵（P0-7）

| 普通聊天新消息 | 保持现有行为 | 保持现有行为（现有 `showNotifyCard` 首行 return 拦截） |

- AI 留言/回复复用 `showNotifyCard(item, force)`（`electron/main.ts:1022`）通道；`item.label` 传语义化标签（如"日记新留言"），`item.content` 或新增字段承载 `日记标题 + 角色名 + 摘要`。

## 9. 验收标准（可度量）

1. **UI**：40 人物时容器高 ≤240px 恒定，仅内部滚动；外层无溢出；checkbox/文字间距 6px、行高一致、长名省略。
2. **一人物一留言**：新建日记开启 AI 并勾选 2 角色 → 默认每角色恰好 1 条留言；再次触发生成 → 无新增（各仍 1 条）。
3. **回复解锁**：对留言 A 回复"我下午去开会了" → AI 立即补 1 条且内容体现该信息；无新回复时不再追加第 2 条 AI 留言。
4. **上下文记忆**：先在该角色单聊里提过"我养了只猫"，再在日记回复中问"还记得我的猫吗" → AI 回复能正确关联（不忘记聊天里的事）。
5. **三类普通触发**：分别配置 window/delay/fixed，各观察一个周期，均按规则触发一次且仅一次；固定点在创建之后创建的日记顺延次日。
6. **NHPP**：启用 NHPP 模式，遵守 `dailyLimit` 与既有门禁；原聊天主动消息行为回归无变化（不回退）。
7. **静默矩阵**：`silent=true` 下连续触发 3 次留言/回复 → 落盘 3 条、通知卡片 0 次、提示音 0 次；`silent=false` 下 3 次 → 3 次提醒且每条文案含日记标题 + 角色名。
8. **通知同级**：AI 留言回复的通知走 `showNotifyCard`，与新消息提醒表现一致（同一卡片样式/队列/去重）。
9. **兼容与不回退**：v3.0.22/23 的日记迁移、门控、身份切换、背景不透明、自适应布局、光标修复、i18n 10 语言、14 主题、文档与版本流程全部保留；旧 `diary.json` 无新字段可正常读取。
10. **收尾**：`package.json` 版本 = 3.0.24；`使用说明.md`/`GuideView.tsx`/`README.md`/`硬编码清单.md`/`版本更新记录.md` 同步；GitHub 上传并打 tag `v3.0.24`。

| # | 问题 | 主理人裁定（已定） |
|---|---|---|
| Q1 | **多轮回复**：AI 回复后能否再次接受用户回复并循环？ | **允许多轮回复**，但**每一轮 AI 回复都必须由用户的新回复触发，绝不自动连发**；`awaitingUserReply` 每轮控制。→ 回灌 §4.1 / §5.2 / §6 |
| Q2 | NHPP 日记留言是否受 `proactiveDnd` 窗口顺延？ | **沿用 `proactiveDnd` 窗口顺延**（原 NHPP 行为不回退）；它与托盘静默 `settings.silent` **语义分离**——静默只管通知，不影响生成。→ 回灌 §4.3 |
| Q3 | 「时段留言」的"某一刻"随机策略与每日次数？ | **时段内均匀随机、每篇每角色每日最多 1 次**，与一人物一留言锁一致。→ 回灌 §4.2 |
| Q4 | 配置变更时对已 `pending` 未发任务如何处理？ | **作废旧 `pending` 并按新配置重排**；关闭 `enabled` → **直接作废**。→ 回灌 §5.1 |
| Q5 | 「手动重新留言」是否受"一人物一留言"锁约束？ | 属用户显式意图，**允许强制重生成**（旧留言软撤 `revoked`），**UI 必须二次确认**。→ 回灌 §4.4 / §6 |
| Q6 | 按人物配置是全局（跨身份）还是按身份？ | **全局按 `roleId`**，不按身份分，与现有 `settings` 结构一致。→ 回灌 §5.1 |
| Q7 | AI 回复注入聊天上下文的条数/范围？ | 上限由**架构师定**，但硬要求「**用户本次回复原文 + 该留言串全部历史**」必须包含；其余按最近 N 条该角色聊天与既有 token 预算裁剪，遵守 `collectArtifactsForRole` 门控，**不注入未授权产物**。→ 回灌 §6 |

## 11. 风险

1. **调度耦合**：新增日记留言任务若挂在同一 60s 心跳上，需避免与原 NHPP 聊天候选互相阻塞（原心跳"每轮只处理一条"限制），建议独立循环或明确优先级。
2. **门控一致性**：留言/回复文本进对话必须持续遵守 `collectArtifactsForRole`（未 revoked、身份册 + 可见名单双门控）；`revoked` 后整串不得再被引用，否则破坏"AI 知道只由可见产物承载"的不变量。
3. **静默口径漂移**：提示音拦截与主进程卡片 return 必须同口径，否则静默下仍响/非静默下漏提醒；改动后需回归现有静默测试。
4. **向后兼容**：`DiaryComment`/`AppSettings` 新字段必须可选，旧存档零迁移可读；避免把新字段写成必填导致老数据崩溃。
5. **i18n 覆盖**：10 语言新增键易漏，需脚本化校验 missing key。
6. **版本/发布流程**：上传 GitHub 与 tag 需遵循既有流程，确认凭据与版本号一致，避免 tag 与 `package.json` 失配。
