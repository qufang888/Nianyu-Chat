## 1. 目标与范围

### 1.1 本轮目标

1. **舞台与桌面一致**：角色舞台里看到的模型大小、清晰度，与桌面上实际显示的桌宠完全对齐（大小同步 + 放大不糊）。
2. **桌宠表现可调**：主动说话频率由硬编码改为「每分钟 N 条」滑块（0~60，0 = 完全不说话）。**滑块即实际目标速率** —— 设定 60 就是 60 条/分钟，不做静默降级、**不显示**「实际约 N 条/分」提示（最终口径见 §12.2）。
3. **动画体系化**：桌宠右键菜单、气泡（弹入 + 缩回）全部纳入「主题与外观 → 动效开关」三档体系，并支持时长细调；气泡停留时长按字数动态计算。
4. **可验证**：所有新增动画均能被现有 `verify:i18n-coverage`、`verify:desktop-character` 闸门与人工验收覆盖。

### 1.2 明确不做（本轮 Out of Scope）

| 不做的事 | 理由 |
|---|---|
| Android / 移动端移植 | 平台无关，本轮只针对 Windows 桌面 |
| 改核心聊天管线（消息落库、流式渲染、AI 请求链路） | 桌宠只是订阅方，改管线会扩大回归面 |

## 2. 逐条需求规格

### R1 — 舞台缩放同步到桌面桌宠

**用户故事**
> As a 桌宠用户, I want 在角色舞台里把「模型大小」滑块拖动时，桌面上的那只桌宠也跟着变大/变小, so that 我在舞台里调好就是最终效果，不用再跑到桌面上用滚轮重新调一遍。

**验收标准**

| 编号 | 标准 |
|---|---|
| R1-AC1 | 舞台「模型大小」滑块取值范围从 **0.6 ~ 1.9** 改为与桌宠 `scale` 一致的 **0.6 ~ 1.6**，步长 **0.05**，两端各留 1 档余量不得越界。 |
| R1-AC2 | 拖动舞台滑块 → 桌面桌宠尺寸**实时**（≤ 150ms，无明显迟滞）跟随变化，无需切窗口/重启。 |
| R1-AC3 | 缩放值通过既有 `dc:set-scale` IPC 写回并持久化到 `settings.desktopCharacters[].scale`，**重启应用后保持**。 |
| R1-AC4 | **反向同步**：在桌面桌宠上用滚轮把尺寸调到 X → 舞台滑块（若处于打开状态）在 ≤ 300ms 内显示 X（百分比文本同步）。舞台必须订阅 `dc:state` / `settings:changed` 事件刷新。 |
| R1-AC5 | 舞台滑块与桌面滚轮**双向同步且不互相回环**：舞台写 → 桌面收到广播 → 桌面不回写触发第二次持久化；同一轮操作内 `saveSettings` 只发生 1 次。 |
| R1-AC6 | 桌宠处于「隐藏 / 未在桌面显示」时，舞台滑块依然可调、依然持久化（写的是配置，不依赖窗口存在）。 |
| R1-AC7 | 舞台缩放**不再**是纯视觉的临时状态：关闭舞台后重新打开，滑块显示的是上次保存值。 |
| R1-AC8 | 舞台内的旋转（拖拽 rotateX/rotateY）保持纯预览语义，**不写回**桌面（桌面不支持旋转）——只同步缩放，不同步姿态。 |

**交互细节与默认值**

- 舞台滑块默认值：取该角色当前 `scale`（缺省 1）。
- 百分比显示：`Math.round(scale * 100)%`，如 `100%`；1.6 → `160%`。
- 舞台「模型大小」文案保持 `characters.stageZoom`（已有 key），仅补一条副文案说明它会同步到桌面（新增 key）。
- 桌面滚轮步长保持 ±0.05、范围 0.6~1.6 不变（v3.0.2 现状）。
- **缩放语义澄清（重要）**：舞台 zoom 当前是"视口内放大"，改成"角色真实大小"后，舞台里的角色在 160% 时会填满舞台视口。舞台视口需允许溢出滚动/自适应，避免角色被裁掉。

**与既有功能的关系 / 冲突点**

- 现状：舞台 zoom 是**组件本地 state**（`CharacterStage.tsx` 的 `useState(1)`），完全不落盘；桌面 `scale` 是**持久化字段**（`DesktopCharacter.scale`，钳制 0.6~1.6）。二者当前**互不相通**，这正是用户报的现象。
- 冲突点 1：**范围不一致**（舞台 0.6~1.9 vs 桌面 0.6~1.6）。本 PRD 统一为 **0.6~1.6**，以桌面为准（桌面窗口 340×420 是硬约束，1.9 会超出窗口可视区）。
- 冲突点 2：桌面滚轮写入 `scale` 后会广播 `settings:changed` + `dc:state`；舞台必须**只读消费**这些广播，不得因为"收到新值"又反向调用 `dc:set-scale`（会打环、也会造成写入风暴）。
- 冲突点 3：`dc:set-scale` 走 `dm.saveSettings({ desktopCharacters: next })`，**整体覆盖数组**。舞台写回时必须传完整数组，不能只传 `{ scale }`，否则会把其它角色的字段清空。
- 冲突点 4：角色面板（`CharacterCollection`）的卡片也订阅 `dc:state`，同步写回后卡片需刷新（现状已有 `onDcState` → `refresh`，无需改动，但需回归验证）。

### R2 — 舞台放大后的清晰度（高清渲染）

**用户故事**
> As a 桌宠用户, I want 在角色舞台里把模型放大到 160% 时看到的是清晰的立绘，而不是糊成一片, so that 舞台能真正当作"预览桌宠最终效果"的工具。

**验收标准**

| 编号 | 标准 |
|---|---|
| R2-AC1 | 舞台放大后**不得**出现由 CSS `transform: scale()` 插值造成的糊化。放大后模型的有效渲染分辨率不低于 `displaySize × devicePixelRatio`。 |
| R2-AC2 | 以 160% 放大一张 ≥190×228 原始像素的立绘，舞台内实际呈现的清晰度 **≥ 桌面上同一角色同尺寸（scale=1.6）的清晰度**（像素级对比边缘锐度，不接受"差不多"）。 |
| R2-AC3 | 缩放后不出现空白边、拉伸变形（aspect-ratio 保持）、图像重采样锯齿（保持平滑插值）。 |
| R2-AC4 | 3D（VRM/GLB）与 Live2D 在舞台放大时同样清晰：其渲染画布的 `pixelRatio` / 渲染分辨率随缩放提升，不得固定在 1x。 |
| R2-AC5 | 缩放过程**流畅**：拖动/滚轮缩放期间无明显掉帧卡顿（1080p 桌面、60Hz 下，缩放交互期间主窗帧率 ≥ 45fps 的观感；不得出现"缩一下卡 200ms"）。 |
| R2-AC6 | 缩放后旋转（拖拽）依然生效，3D 姿态不变形。 |
| R2-AC7 | 舞台放大不影响桌面上桌宠的实际清晰度与性能（桌宠窗是独立 document，渲染路径不共用）。 |

**交互细节与默认值**

- 建议实现方向（供工程参考，非强制）：把「视口缩放」与「素材分辨率」解耦——
  1. 位图角色（image/sprite）：读取素材**原始像素尺寸**，按 `原始尺寸 × zoom × devicePixelRatio` 决定渲染栅格尺寸，让浏览器在高分辨率下重采样，而不是拉伸一个 190×228 的低分辨率位图；
  2. 矢量角色（placeholder/SVG）：本身分辨率无关，保持 `transform: scale()` 即可；
  3. 3D/Live2D：把 zoom 传入渲染器，用于放大渲染目标分辨率（`setPixelRatio` / 画布尺寸）。
- 舞台视口在 R1 改造后需要能容纳 190×228 × 1.6 = 304×365 的角色：视口建议最小高度 380px，超出时允许纵向滚动。
- 缩放不改变模型在舞台里的**定位锚点**（仍底部居中）。

**与既有功能的关系 / 冲突点**

- 现状：`CharacterStage.tsx` 用 `transform: perspective(900px) rotateX() rotateY() scale(${zoom})` 作用在 `.stage-model`（固定 190×220 的盒子）上；内层 `<img>` 以 `object-fit: contain` 按 190×220 布局，CSS 放大必然走插值 → **这就是"很模糊"的根因**。
- 桌面上桌宠清晰的原因：桌宠是**独立 BrowserWindow（`character.html`）**，窗口按 `scale` 调整了实际尺寸/由系统按窗口尺寸以原生分辨率合成，不存在"先按小尺寸栅格化再 CSS 放大"的路径。所以用户"应该跟桌面一样"的直觉是**正确的**，本轮就是要把舞台的渲染路径对齐桌宠。
- 冲突点：`.stage-model` 同时承载了 **rotate（舞台专属预览能力）** 与 **scale**。R1 要求 scale 变成"真实尺寸"，但 rotate 仍是纯预览。两者叠加时不能简单把 scale 摘掉——否则旋转的手感会变。因此实现上需把「尺寸语义」与「旋转变换」分层处理（见 §4.3 建议）。
- 冲突点：`src/styles/character-panel.css` 里 `.stage-model .dc-svg { animation: none }` —— 舞台已主动关掉占位角色的呼吸动画（R2 不改变这一点，但改造时不得把它带回来）。

### R3 — 桌宠主动说话频率可调（每分钟 N 条）

**用户故事**
> As a 桌宠用户, I want 用一个滑块调节桌宠主动说话的频率（按"每分钟几条"计），并且能完全关成 0, so that 我能让它话多、话少，或者干脆闭嘴，而不用去改代码。

**验收标准**

| 编号 | 标准 |
|---|---|
| R3-AC1 | 提供 **0 ~ 60 条/分钟** 的滑块（`input[type=range]`，step = 1），0 为合法值。 |
| R3-AC2 | 语义为**每分钟条数**（不是"每隔多少秒"）。换算关系：`intervalMs = 60000 / N`（N=60 → 1000ms；N=30 → 2000ms；N=1 → 60000ms；N=0 → **不发起任何请求**）。`intervalMs` 是频率调度的**唯一真值源**。 |
| R3-AC3 | N=0 时，桌宠**完全不发起**主动说话请求（无模型调用、无气泡、无写入绑定对话），且不产生任何后台定时器空转。 |
| R3-AC4 | N>0 时，调度器**以设定值为目标**按 `intervalMs` 发起下一次请求（实际频率的验收口径见 R3-AC5）。 |
| R3-AC5 | **频率验收口径（用户已拍板，不得改口径）**：滑块设定 **60 → 实际请求频率应达到 60 次/分（±1，受 QPS 限流排队影响时以排队完成为准）**。 |
| R3-AC6 | **滑块即实际目标速率**：UI **不得**出现「实际约 N 条/分钟」「受请求耗时限制」等折中提示，也不得出现"滑块 ≠ 实际速率"的任何暗示。滑块显示 N，目标就是 N。 |
| R3-AC7 | 单次生成失败/超时**不触发补偿重试**（不立即补发、不加倍打），下一次调度仍按 `intervalMs` 节奏；同时**必须**保留并发锁（同一时刻最多 1 个在途请求）。 |
| R3-AC8 | 频率设置**持久化**，重启后生效；存储在角色级（每个角色可独立设置），与现有 `behavior`（自主行为）开关并存。 |
| R3-AC9 | 频率设置**实时生效**：修改后无需重启应用，下一次调度即按新频率执行。 |
| R3-AC10 | `behavior === false` 或 `bubble === false` 时，优先级高于频率设置（不生成、不弹气泡），与 v3.0.2 现状一致。 |
| R3-AC11 | 拖拽中 / 右键菜单打开时**不生成**（沿用现状的保护逻辑），但该次跳过**不**重排后续节奏。 |
| R3-AC12 | **实现要求 (a) —— 并发锁**：保留**每角色并发锁**，同一时刻只允许一个在途请求（渲染层 `lineInFlightRef` + 主进程 `characterLineInFlight` **双层都保留**）。 |
| R3-AC13 | **实现要求 (b) —— 最小请求间隔**：保留最小请求间隔作为**异常保护**，但下限**不得低于 1000ms**（= 最多 60 条/分，与用户口径一致）。现渲染层 `45_000ms`、主进程 `30_000ms` **均超限，必须改造为派生值**。 |
| R3-AC14 | **实现要求 (c) —— 复用既有 QPS 限流与排队**：必须继续走 `chats:proactive` → `dispatchProactive` → `handleProactive` → `enqueueAndWait(cfg.id, cfg.qps, '主动消息')` → `queryAI`，**不得绕过限流直接打模型**。 |
| R3-AC15 | **实现要求 (d) —— 同源派生**：探测 tick 与最小间隔**必须由同一个 `intervalMs` 派生**，不得各自独立写死（详见「替换方案」）。 |
| R3-AC16 | **实现要求 (e) —— 0 = 完全不主动说话**：N=0 时连调度器都不启动（不设定时器），零请求、零气泡、零写库、零定时器。 |
| R3-AC17 | **排队表现**：受模型 QPS 限流而排队时，表现为**对话里的主动发言延后到达**，但**不会丢消息**（队列按序放行）。 |

**计数口径（用于 R3-AC5 验收，避免歧义）**

- 计数基准 = **请求发起（放行并实际发往模型）的时刻**，不是模型返回时刻。
- "60 次/分" = 任意连续 1 分钟窗口内**发起的桌宠语句请求数 = 60（±1）**。
- QPS 排队等待发生在发起**之前**，因此"以排队完成为准"= 以排队放行后的发起时刻计；排队时长体现为**延后**，不体现为**丢失**。
- 请求**已发起即计数**（失败也占用了模型额度），但失败**不触发补偿性补发**（见 R3-AC7）。
- QA 须能区分「频率不对」与「模型失败/模型慢」两类问题：前者是调度缺陷，后者是模型侧耗时。

> **⚠️ 风险（必须如实写明，不得隐藏、不得用 UI 文案掩盖）**
>
> 1. **费用与调用量**：60 条/分 ≈ 每分钟 60 次模型调用（每小时约 3600 次），token 消耗与费用显著上升。UI 保留成本提示（N ≥ 20 时警示色 + `characters.speakRateWarn`），该提示**只讲成本**，不涉及"实际速率"。
> 2. **排队（不丢消息）**：模型 QPS 配额被其它对话 / 后台任务占用时，桌宠语句会进入既有队列（排队面板标签「主动消息」），表现为**发言延后到达**，但**不会丢消息**。
> 3. **物理上限（如实披露）**：并发锁（同时仅 1 个在途）+ 单次生成耗时共同决定实际可达上限。当模型单次耗时 > 1s 时，60 次/分的**发起频率**会低于目标值 —— 此时 QA 须如实记录"受限于模型耗时"，**严禁**改 UI 口径（如显示「实际约 N 条/分」）来掩盖。
> 4. **服务端 429**：不得为提高频率而绕过 `enqueueAndWait`；宁可排队延后，也不得触发服务端限流。

**交互细节与默认值**

- 控件位置：**角色面板卡片内**（`CharacterCollection.tsx` 的 `dc-coll-toggles` 附近），紧邻「自主行为 / 气泡」两个勾选框，标签：`主动说话频率`。
- 控件形态：滑块 + 右侧数值文本 `N 条/分钟`；N=0 时数值显示 `已关闭`。
- 旁附一行灰色提示：`每分钟最多主动说几句，0 = 不主动说话`。
- **禁止项（用户已拍板）**：数值文本旁**不得**出现「实际约 N 条/分钟」「受请求耗时限制 / 实际生效 X 条/分」等任何折中提示；**不新增**相关 i18n 文案 key。
- 鼠标滚轮在滑块上**不得**改变数值（避免与页面滚动打架）。
- **默认值**：存量用户升级后默认 **2 条/分钟**（派生间隔 30000ms，与主进程原 30s 护栏同值；v3.0.2 观感为 45 秒一次 ≈ 1.33 条/分，取 2 略活跃但仍在同一量级）。新增角色默认同为 2。

**与既有功能的关系 / 冲突点**

- **现状 · 渲染层**（`src/character/CharacterApp.tsx`）：`CHARACTER_LINE_TICK_MS = 15_000`（试探周期）+ `CHARACTER_LINE_MIN_INTERVAL_MS = 45_000`（最小间隔）两个**硬编码常量**；另有 `lineInFlightRef`（并发锁）、`lineLastAtRef`（上次发起时间戳）、`CHARACTER_LINE_TIMEOUT_MS = 20_000`（软超时）。
- **现状 · 主进程**（`electron/main.ts`）：`CHARACTER_LINE_MIN_GAP_MS = 30_000`（**第二道防线**，防桌宠窗重建 / 多窗口并存 / 异常重入绕过渲染层节流）+ `characterLineInFlight`（主进程并发锁）；`chats:proactive` → `dispatchProactive` → `handleProactive` → `enqueueAndWait(cfg.id, cfg.qps, '主动消息')` → `queryAI`。

**替换方案（三者同源派生，不得各自独立）**

1. **唯一派生源**：`targetIntervalMs = N > 0 ? Math.max(60000 / N, 1000) : 0`（0 = 关闭）。建议封装为单一真值函数（如 `deriveLineSchedule(n)` → `{ intervalMs, tickMs }`），**禁止**再出现任何独立写死的时间常量。
2. **最小请求间隔**（替代 `CHARACTER_LINE_MIN_INTERVAL_MS`）= `targetIntervalMs`。
3. **探测 tick**（替代 `CHARACTER_LINE_TICK_MS`）= `clamp(targetIntervalMs / 4, 500, 15000)`（N=60 → 500ms；N=30 → 500ms；N=20 → 750ms；N=10 → 1500ms；N=2 → 7500ms；N=1 → 15000ms 封顶）。tick 只负责"到点检查"，**是否真的发起**由 `now - lastAt >= targetIntervalMs` 判定 —— tick 本身**不产生**任何请求。
4. **主进程第二道防线**（替代 `CHARACTER_LINE_MIN_GAP_MS`）= **该角色**派生的 `targetIntervalMs`（下限 1000ms），**不再是固定 30s**，也不再是全局不分角色的常量。
   > **这是 60 条/分能否达成的关键路径**：`30_000ms` 若保留，N=60 会被硬压到 ≤ 2 次/分，直接违反 R3-AC5。方案二选一，**工程师须在实现说明中写明采用哪一个**：
   > - **方案 A（推荐）**：`chats:proactive` 的参数增加 `targetIntervalMs`（由渲染层按角色算出后随请求携带），主进程按 `max(1000, targetIntervalMs)` 做第二道防线。
   > - **方案 B**：主进程读取 `settings.desktopCharacters` 中该角色的频率设置自行派生。
   > - 无论哪种：主进程护栏**不得**再固定 30s，也**不得**高于渲染层派生值（否则后端成为瓶颈）。
5. **角色级字段**：`DesktopCharacter` 增加 `speakRate?: number`（0~60，缺省 2），持久化于 `settings.desktopCharacters[]`；写入遵守 HC-8「整数组覆盖」。
6. **被节流时不补偿**：主进程返回 `throttled`（被护栏拦截）时，渲染层**不得**立即重试、**不得**补打；下一次仍按 `targetIntervalMs` 节奏（否则会打爆队列）。

**其它冲突点**

- 冲突点 1：频率常量与 `animControl.ts` 的动效体系**无关**（是行为节流，不是动画），不要塞进动效设置（避免语义混淆）。
- 冲突点 2：桌宠主动说话走 `api.proactive({ source: 'character' })` → 主进程 `chats:proactive` → 写入绑定对话为 `from_proactive` 消息。**主进程已过滤 `from_proactive` 不推给气泡**（`pushChatMessageToCharacters`），因此频率调高**不会**导致气泡双弹；这条链路在改造中必须保持。
- 冲突点 3：频率调高会显著增加模型调用量与 token 消耗 —— UI 保留成本提示（N ≥ 20 时警示色 + `characters.speakRateWarn`），提示**只讲成本**，不讲"实际速率"。

### R4 — 桌宠右键菜单弹入/弹出动画（含动效设置细调）

**用户故事**
> As a 桌宠用户, I want 右键菜单打开是"弹入"、关闭是"收回"的动画，而且这些动画的时长我自己能在设置里调, so that 菜单不再像"啪"地闪现，且动效风格由我统一控制。

**验收标准**

| 编号 | 标准 |
|---|---|
| R4-AC1 | 右键菜单**打开**播放弹入动画（`dcMenuIn`），**关闭**播放收回动画（`dcMenuOut`），两条路径都必须肉眼可辨。 |
| R4-AC2 | 收回动画结束后菜单才卸载（当前 v3.0.2 已是此逻辑，收回态 `pointer-events: none`，保留）。 |
| R4-AC3 | 当"全部关闭"档生效时，菜单**立即出现/立即消失**（无动画），且**不得**出现"关不掉 / 菜单卡住"的故障（现状 `closeMenu` 已有 `animOff` 提前卸载分支，需回归）。 |
| R4-AC4 | 菜单动画纳入 `animControl.ts` 的 `character` 分组（`docSelectors.character` 已含 `.dc-menu`），**自定义档关闭 `character` 组时菜单动画失效但菜单功能正常**。 |
| R4-AC5 | 菜单动画时长**可在设置里细调**：菜单动画时长滑块，范围 **0.05s ~ 1.0s**，步长 **0.05s**，默认 **0.20s**（用户已拍板：由 v3.0.2 的 0.14s 上调，使动画肉眼可辨；**必须同步更新闸门脚本的字面量断言**，见 HC-5）。 |
| R4-AC6 | 时长值**实时生效**：在设置里调整后，下一次打开/关闭菜单即采用新时长（不需要重启）。 |
| R4-AC7 | 设置里的时长调整**必须同时作用于 CSS 与 JS 两侧**（JS 侧的延迟卸载计时必须同步换算，否则会出现"菜单动画播到一半凭空消失"或"关不掉"）。这是本条最容易出 bug 的点。 |
| R4-AC8 | 菜单动画**受全局/分组速度倍率影响**（`--anim-speed`），与项目既有动效体系一致；角色窗 CSS 目前**未接** `--anim-speed`（见 `CharacterApp.tsx` 注释），本轮需补上，使三档 + 倍率 + 细调三者叠加后行为自洽。 |
| R4-AC9 | 菜单动画幅度**加 `scale 0.96→1`**（用户已拍板），缓动**保持 linear**：弹入 `dcMenuIn` = `opacity 0→1 + translateY 6px→0 + scale 0.96→1`，收回 `dcMenuOut` 反向播放。 |
| R4-AC10 | **排查要求（不可省略、不可假设"没实现"）**：实现时必须**逐条排查**下列四个可能原因，并在实现说明中给出**实证结论**（到底是哪一个 / 哪几个）：① 三档开关被关（全部关闭档，或自定义档未勾 `character` 组）；② `prefers-reduced-motion: reduce`；③ 时长与幅度太弱；④ 点菜单项时收回动画被业务动作盖过。若四条**全部排除**，须给出新的根因分析。**未给出实证结论不得视为交付完成。** |

**交互细节与默认值**

- 设置位置：**主题与外观 → 高级设置 → 动效分组**（`sec-anim-control` 区域）内，`character` 分组（`animCtl.groupCharacter`）一行之下，展开「桌宠动画细调」子块。
- 子块内控件：
  1. **菜单弹出/收回时长**：单个滑块（弹入与收回共用同一时长，保证对称），`0.05s ~ 1.0s`，步长 `0.05s`，默认 **`0.20s`**；右侧显示 `0.20s`。
  2. **气泡弹出时长**（R5/R6 复用）：`0.05s ~ 1.0s`，默认 `0.18s`。
  3. **气泡停留时长基准 / 每 20 字递增 / 上限**（R6 复用）：三个参数**全部开放**，见 R6 交互细节。
- **可见性（用户已拍板，Q3）**：本子块**全部可调，但只在「自定义」档渲染/可见**（与分组开关同规则）；「全部开启 / 全部关闭」档下**不渲染**，用户需先切到「自定义」档才能细调（见 §12.3）。
- **生效语义**：自定义档内，细调值仍受该组开关与速度倍率约束 —— 若 `character` 组被关，细调值不生效，需在该子块内**明示**（沿用设置页既有的 `disabled + 说明` 范式，不做静默失效，HC-7）。

**与既有功能的关系 / 冲突点**

- 现状：v3.0.2 **已经实现了** `dcMenuIn / dcMenuOut`（`src/styles/character.css`）与 JS 侧 `DC_MENU_ANIM_MS = 140` 的延迟卸载。用户反馈"没有弹入弹出动画"——本轮需按 **R4-AC10 的四原因逐条排查** 定位真实原因并给出**实证结论**，不得直接假设"没实现"（下表 A~D 与 §12.4 的 ①~④ 一一对应）：
  - 可能性 A ＝ ①：用户处于「全部关闭」档或自定义档未勾 `character` 组 → 动画被门控掉（**最可能**）；
  - 可能性 B ＝ ②：`prefers-reduced-motion: reduce`（Windows「显示效果」关闭）下 `@media` 规则强制 `animation: none`；
  - 可能性 C ＝ ③：0.14s 线性 + 4px 位移的动效**幅度太小/时长太短**，肉眼确实看不出"弹入"，被感知为"没有动画"；
  - 可能性 D ＝ ④：收回动画只在"点外部/Escape"路径播放，点菜单项时 `closeMenu()` 与 `m.onClick()` 同时执行、菜单瞬间被业务动作盖过，用户看不到收回。
- **本轮对策（必须全部落实）**：
  1. 动画**幅度**加大并保持线性（用户偏好线性）：`dcMenuIn` 从 `opacity 0→1 + translateY 4px→0` 改为 `opacity 0→1 + translateY 6px→0 + scale 0.96→1`（**已拍板，确定执行**，非可选）；
  2. 默认时长从 0.14s **上调到 0.20s**（≥150ms 才容易被感知），并开放细调（**已拍板**）；
  3. 走**设置页**路径时，若动画开关处于关闭档，设置页需明示「桌宠菜单动画当前被『动效开关』关闭」；
  4. **收回归属**：点菜单项时，**先播完收回动画再执行该项业务动作**（如"隐藏角色""打开舞台"），让用户能看到收回过程（该项动作本身有窗口切换，延迟 0.2s 可接受）。
- 冲突点：`scripts/verify-desktop-character.mjs` 有硬断言 `/animation: dcMenuIn 0\.14s linear/` 与 `/DC_MENU_ANIM_MS = 140/`。**改默认值必须同步更新该闸门脚本**（改为 `dcMenuIn 0\.20s linear` / `dcMenuOut 0\.20s linear forwards` / `DC_MENU_ANIM_MS = 200`），否则 CI 红灯。

### R5 — 气泡弹出 + 缩回动画

**用户故事**
> As a 桌宠用户, I want 桌宠气泡是"弹出来"的，走的时候是"缩回去"的，而不是啪地消失, so that 桌宠的对话有来有回，像真的在跟我说话。

**验收标准**

| 编号 | 标准 |
|---|---|
| R5-AC1 | **两类来源**的气泡都必须带完整动画：① 绑定对话来了新消息（`dc:chat-message` 推送）；② 桌宠主动说的话（`requestCharacterLine` 生成）。 |
| R5-AC2 | 气泡**弹入**：从透明 + 轻微上移/缩放的状态过渡到终态，默认 0.18s（沿用 v3.0.2 的 `dcBubbleIn`）。 |
| R5-AC3 | 气泡**缩回**：停留结束后播放收回动画（新增 `dcBubbleOut`），默认 0.18s，动画结束后才卸载 DOM。 |
| R5-AC4 | 收回动画播放期间，气泡**不接收点击**（`pointer-events: none`），避免"缩回中还能点"导致的误触。 |
| R5-AC5 | 收回动画播放期间，**新气泡到来**应立即打断收回、切换为新气泡（不得出现"新消息被旧气泡的收回动画吞掉"）。 |
| R5-AC6 | 气泡的点击关闭（点 `.dc-bubble-text` 收起）同样走**缩回动画**，不是瞬间消失。 |
| R5-AC7 | 三档门控：「全部关闭」档 → 气泡**瞬间出现/瞬间消失**（无动画但功能完整）；自定义档关掉 `character` 组 → 同上；全部开启 → 播放完整双向动画。 |
| R5-AC8 | 气泡动画元素必须在 `docSelectors.character` 中登记（`.dc-bubble` 已登记；新增的 `.dc-bubble.closing` 形态需被同一条规则覆盖 —— 注意 `html[data-anim-off~='character'] .dc-bubble` 选择器**已能**命中带 `closing` 类的元素，但需在闸门脚本中新增断言防止后续改类名时静默失效）。 |
| R5-AC9 | 角色窗 CSS **不加载** `index.css`，其 `html.anim-off` / `html[data-anim-off~='character']` 兜底规则**独立写在 `character.css`** —— 新增的 `.dc-bubble.closing` 必须被这两条兜底规则覆盖（否则关档后收回动画仍在播）。 |

**交互细节与默认值**

- 弹入 / 收回默认时长均为 **0.18s**（与 v3.0.2 弹入一致），缓动保持 **linear**（用户既有偏好）。
- 收回时的位移方向与弹入相反（弹入从下 +4px 上移进入 → 收回向上 +4px 淡出），形成"进/出"的方向感。
- 「气泡缩回」期间气泡仍占位（不塌陷），避免角色头顶位置跳动。

**与既有功能的关系 / 冲突点**

- 现状：`.dc-bubble` 只有 `animation: dcBubbleIn 0.18s linear`，**没有收回态**。`showBubble()` 用 `setTimeout(() => setBubble(null), ms)` 直接卸载 → 气泡是"啪"地消失的。这就是用户要"缩回动画"的缺口。
- 冲突点 1：菜单的收回已经实现了「加 `.closing` 类 → 播 `dcMenuOut` → 延迟卸载」的范式（`menuClosing` state + `DC_MENU_ANIM_MS` 计时器）。气泡**必须复用同一范式**，不要另创一套。
- 冲突点 2：气泡收回的延迟卸载计时必须与 CSS 时长**同源换算**（`animMs()` 或等价的"CSS 基准秒数 × 倍率"），否则速度调快/调慢都会出现"闪一下不见 / 卡住不消失"。
- 冲突点 3：气泡有**两条触发路径**（新消息 / 主动说话），共用同一个 `showBubble()`，因此动画与时长只需在一处实现 —— 但计时器必须在两处都正确清理（现有 `bubbleTimer` 复用同一 ref，注意 clearTimeout）。
- 冲突点 4：`.dc-bubble` 已登记在 `character` 分组的 `docSelectors.character`，**不要**把气泡挪到 `bubble` 组（`bubble` 组是主窗消息气泡的语义），否则用户在自定义档关 `bubble` 组会误伤桌宠气泡。

### R6 — 气泡停留时长按字数动态计算

**用户故事**
> As a 桌宠用户, I want 桌宠说的长句子能在屏幕上多停一会儿，短句快速让位, so that 长台词不会一晃就没、我还没看清。

**验收标准**

| 编号 | 标准 |
|---|---|
| R6-AC1 | 停留时长按**气泡文本字数**分档计算（分档表见下）。**计数口径**：按 `sanitizeBubbleText()` 处理后的**展示文本**的字符数计（Unicode 码点，中文按 1 字计，标点计入，空白已由 sanitize 合并剔除）。 |
| R6-AC2 | 分档表（**基准 3s / 每档 +1s / 上限 10s**）：<br>`≤20 字 → 3s`；`21~40 → 4s`；`41~60 → 5s`；`61~80 → 6s`；`81~100 → 7s`；`101~120 → 8s`；`121~140 → 9s`；`>140 → 10s（封顶）` |
| R6-AC3 | 计算公式：`duration = clamp(BASE + floor(max(0, len - 20) / 20), BASE, MAX)`（等价于分档表，边界值 20/40/60… 必须落在下一档，如 21 字 → 4s、40 字 → 4s、41 字 → 5s）。 |
| R6-AC4 | 停留时长从**气泡出现（弹入开始）**起算，到**缩回动画开始**为止；**弹入与缩回动画的时长额外叠加**在停留时长之外（总可见时长 = 停留 + 弹入 + 缩回）。 |
| R6-AC5 | 新消息气泡与主动说话气泡**共用同一套计算**（同一函数），不得各算各的。 |
| R6-AC6 | 三个参数（**基准 / 每 20 字递增秒数 / 上限**）**全部开放**给用户（用户已拍板，Q5），在动效设置里可细调：<br>· 基准停留：1 ~ 10s，步长 0.5s，默认 **3s**<br>· 每 20 字递增：0 ~ 3s，步长 0.5s，默认 **1s**<br>· 停留上限：3 ~ 30s，步长 1s，默认 **10s**<br>默认值精确匹配用户口径：**>20 字弹 3 秒以上，每增加 20 字多弹 1 秒，最多 10 秒**。 |
| R6-AC7 | 上限必须**真正生效**：文本 500 字时停留封顶在 10s（可调后的封顶值），不得线性外推。 |
| R6-AC8 | 三个参数**持久化**且**实时生效**。 |
| R6-AC9 | 气泡文本在**两条路径下的长度上限不同**（主动说话路径 80 字，新消息路径主进程侧 120 字），因此实际可达的最长停留档位不同；本轮**不统一**这两个上限（不在范围内），但 QA 需按各路径的真实上限验证分档。 |

**交互细节与默认值**

- 设置位置：同 R4 的「桌宠动画细调」子块，三个滑块并列一行，标注：`基准停留` / `每 20 字 +` / `上限`。
- 右侧实时显示换算示例（如 `60 字 ≈ 5.0s`），让用户能预估效果。
- 参数语义在设置页用一行说明文字讲清：`气泡停留时长按字数分档：基准 X 秒，每多 20 字 +Y 秒，最多 Z 秒`。
- 建议在设置项旁加一个「预览」小按钮，点一下在舞台/角色面板区弹一个示例气泡，让用户当场看到时长效果。

**与既有功能的关系 / 冲突点**

- 现状：两处硬编码 —— `CHARACTER_BUBBLE_MS = 4200`（主动说话路径）与 `showBubble(text, ms = 3800)` 的默认参数（新消息路径传 `CHARACTER_BUBBLE_MS`）。两者**不一致**（4200 vs 3800），本轮统一为按字计算。
- 冲突点 1：R6-AC4 的"总可见时长 = 停留 + 弹入 + 缩回"意味着**用户看到的实际停留比设定值长约 0.36s**。这是可接受的（动画本身也要时间），但 QA 测量时应区分"停留计时"与"总可见时长"。
- 冲突点 2：分档计时的**计时器起点**必须是"气泡挂载时刻"，不能是"模型返回时刻"，否则生成耗时会从停留时间里扣。
- 冲突点 3：与 R5 的缩回动画串联 —— 计时器到点后**不立刻卸载**，而是切到 `.closing` 态播缩回动画，动画结束再卸载。

### 12.2 Q2 — 频率量程（**字面实现 0 ~ 60 条/分钟**）

**结论**

- 频率**字面实现 0~60 条/分钟**。**滑块设定值 = 实际目标速率**：用户要 60 条/分钟，就是 60 条/分钟。
- **取消** UI 上的「实际约 N 条/分钟」提示，以及一切"滑块 ≠ 实际速率"的折中设计。**不新增**相关 i18n 文案。
- **换算关系（唯一真值源）**：`intervalMs = 60000 / N`
  - N=60 → **1000ms**；N=30 → 2000ms；N=20 → 3000ms；N=10 → 6000ms；N=1 → **60000ms**；N=0 → **不请求**。

**实现要求（必须全部落实）**

| 编号 | 要求 | 说明 |
|---|---|---|
| (a) | **保留每角色并发锁** | 同一时刻只允许一个在途请求。渲染层 `lineInFlightRef` + 主进程 `characterLineInFlight` **双层均保留**，不得因提频而放宽。 |
| (b) | **保留最小请求间隔**（异常保护） | 下限**不低于 1000ms**（= 最多 60 条/分，与用户口径一致）。现渲染层 `45_000ms`、主进程 `30_000ms` **均超限，必须改造为派生值**。 |
| (c) | **必须复用软件既有的模型 QPS 限流与排队机制** | 继续走 `chats:proactive` → `dispatchProactive` → `handleProactive` → `enqueueAndWait(cfg.id, cfg.qps, '主动消息')` → `queryAI`；**不得绕过限流直接打模型**。 |
| (d) | **验收标准** | 滑块设定 **60 → 实际请求频率应达到 60 次/分（±1，受 QPS 限流排队影响时以排队完成为准）**。计数基准 = **请求发起时刻**（排队放行后发起即计）；失败**不触发补偿重试**。 |
| (e) | **0 = 完全不主动说话** | N=0 时连调度器都不启动（不设定时器）：零请求、零气泡、零写库、零定时器。 |

**派生方案（tick 与最小间隔同源，不得各自独立）**

- `targetIntervalMs = N > 0 ? Math.max(60000 / N, 1000) : 0`（0 = 关闭）—— 建议封装为单一真值函数（如 `deriveLineSchedule(n)` → `{ intervalMs, tickMs }`）。
- **最小请求间隔**（替代 `CHARACTER_LINE_MIN_INTERVAL_MS`）= `targetIntervalMs`。
- **探测 tick**（替代 `CHARACTER_LINE_TICK_MS`）= `clamp(targetIntervalMs / 4, 500, 15000)`（N=60 → 500ms；N=30 → 500ms；N=20 → 750ms；N=10 → 1500ms；N=2 → 7500ms；N=1 → 15000ms 封顶）。tick 只做"到点检查"，**是否发起**由 `now - lastAt >= targetIntervalMs` 判定；tick 本身**不产生**请求。
- **主进程第二道防线**（替代 `CHARACTER_LINE_MIN_GAP_MS`）= **该角色**派生的 `targetIntervalMs`（下限 1000ms），**不再是固定 30s**、不再是全局不分角色的常量。
  - ⚠️ **这是 60 条/分能否达成的关键路径**：`30_000ms` 若保留，N=60 会被硬压到 ≤ 2 次/分，直接违反 (d)。
  - 方案 A（推荐）：`chats:proactive` 参数增加 `targetIntervalMs`（渲染层按角色算出后携带），主进程按 `max(1000, targetIntervalMs)` 拦截。
  - 方案 B：主进程读取 `settings.desktopCharacters` 中该角色的频率设置自行派生。
  - 无论哪种：主进程护栏**不得**固定 30s，也**不得**高于渲染层派生值（否则后端成瓶颈）。**方案选型须写入实现说明。**
- **角色级字段**：`DesktopCharacter` 增加 `speakRate?: number`（0~60，缺省 2），持久化于 `settings.desktopCharacters[]`（遵守 HC-8 整数组覆盖）。

**风险（必须如实写明，不得隐藏）**

1. **费用与调用量**：高频调用会**显著增加模型调用量与费用**（60 条/分 ≈ 每分钟 60 次模型调用，每小时约 3600 次）。UI 保留成本提示（N ≥ 20 警示色 + `characters.speakRateWarn`），提示**只讲成本**。
2. **排队（不丢消息）**：在 QPS 限流下可能出现**排队**，表现为**对话里的主动发言延后到达**，但**不会丢消息**（队列按序放行）。
3. **物理上限（如实披露）**：并发锁（同时仅 1 个在途）+ 单次生成耗时共同决定实际可达上限。当模型单次耗时 > 1s 时，60 次/分的**发起频率**会低于目标值 —— 此时 QA 须如实记录"受限于模型耗时"，**严禁**改 UI 口径来掩盖。
4. **服务端 429**：不得为提高频率而绕过 `enqueueAndWait`；宁可排队延后，也不得触发服务端限流。

**落点**：R3-AC1 ~ R3-AC17（含计数口径与风险块）、§4.1、HC-9、§7.2 · C1 ~ C13、§8 附录。

### 12.4 Q4 — 菜单动画"看得见"

- **结论**：默认时长 **0.14s → 0.20s**；幅度加 **`scale 0.96→1`**；缓动**保持 linear**。
  - `dcMenuIn`：`opacity 0→1 + translateY 6px→0 + scale 0.96→1`，`0.20s linear`；`dcMenuOut` 反向，`0.20s linear forwards`；JS 侧 `DC_MENU_ANIM_MS = 200`（与 CSS 同源换算）。
- **排查要求（不可省略、不可假设"没实现"）**：用户反馈"看不到动画"，实现时必须**逐条排查**下列四个可能原因，并在**实现说明中给出实证结论**（到底是哪个原因 / 哪几个，附复现步骤）：

  | # | 可能原因 | 排查方式 |
  |---|---|---|
  | ① | **三档开关被关** —— 处于「全部关闭」档，或自定义档未勾选 `character` 组 | 读 `document.documentElement` 的 `data-anim-off` / `html.anim-off` 实际取值 |
  | ② | **`prefers-reduced-motion: reduce`**（Windows「显示效果」关闭）→ `@media` 规则强制 `animation: none` | DevTools 模拟该媒体特性，对比动画是否消失 |
  | ③ | **时长与幅度太弱** —— 0.14s 线性 + 4px 位移肉眼不可辨 | 对比 0.14s/4px 与 0.20s/6px+scale 的观感差异 |
  | ④ | **收回动画被业务动作盖过** —— 点菜单项时 `closeMenu()` 与 `m.onClick()` 同时执行，菜单瞬间被业务动作覆盖 | 逐个菜单项点，观察收回过程是否被覆盖 |

  - 若四条**全部排除**，须给出新的根因分析。
  - **未给出实证结论不得视为交付完成。**（§7.2 · D9）
- **落点**：R4-AC5 / R4-AC9 / R4-AC10、R4 对策 1~2、§4.2、HC-5、§7.2 · D2 / D9、§8 附录。

### 12.5 Q5 — 气泡时长参数暴露（三个参数全部开放）

- **结论**：**基准停留 / 每 20 字增量 / 上限** 三个参数**全部开放**给用户细调。
- 默认值 **3s / 1s / 10s**，**精确匹配用户口径**：>20 字弹 3 秒以上，每增加 20 字多弹 1 秒，最多 10 秒。
  - 范围：基准 1~10s（步长 0.5s）；每 20 字 0~3s（步长 0.5s）；上限 3~30s（步长 1s）。
- 计算公式不变：`duration = clamp(BASE + floor(max(0, len - 20) / 20), BASE, MAX)`。
- **落点**：R6-AC2 / R6-AC3 / R6-AC6、R4 交互细节、§4.2、§4.4 i18n、§7.2 · F1 ~ F7。
